# 判斷力守則（judgment.md）

> 讀者：主對話的模型（任何等級）。每條 rubric 附判準、正例、反例。
> 例子是判準的一部分——不確定某條怎麼適用時，找最像的例子照做。

## R1 何時升級模型

**判準**（符合任一即升級，路徑照 `dispatch.md` 第 4 節）：
- 同一子任務用不同做法失敗 2 次
- 修 A 壞 B、修 B 壞 C 的連鎖出現 2 次（打地鼠訊號）
- 任務涉及跨模組的設計取捨、資料模型變更、或安全性
- 你發現自己在「猜」而不是在「推導」——寫不出失敗的因果解釋，只能列可能性

✅ 正例：sonnet 修 hydration error，第一次改 useEffect 沒好，第二次改 dynamic import
反而多了新錯誤 → 帶完整軌跡（兩次改法＋錯誤全文）派 `second-opinion`（opus）。
❌ 反例：lint 報 `no-unused-vars`，第一次修錯就升級 opus——lint 錯誤訊息已經寫明答案，
該做的是重讀錯誤訊息，不是升級。**升級解決的是判斷力不足，不是粗心。**

## R2 何時算真的完成

**全部滿足才算完成**：
1. 開工時列的驗收條件逐條通過（沒列驗收條件 = 開工程序就錯了，先補列）
2. 機器證據在手：`npm run lint && npx tsc --noEmit && npm test` 通過；
   改 UI 流程 → `/verify` 實跑過；改 firestore.rules → `npm run test:rules` 通過
3. `git diff --stat` 檢查過：diff 只含本任務需要的變更
4. 非瑣碎變更由 `verifier` agent 驗收回 `VERDICT: PASS`
5. 給使用者的回報含證據，不是只有宣稱

✅ 正例回報：「修改 `src/views/ApplyForm.tsx:112-130`，lint/typecheck/test 全過，
/verify 實跑申請流程成功送出，diff 僅 2 檔。」
❌ 反例回報：「我已經修改了驗證邏輯，應該可以了。」——「應該」= 未完成。
❌ 反例行為：跑了 `npm run build` 看到 exit 0 就宣告 UI 改好——build 過 ≠ 畫面對。

## R3 何時停下來問使用者

**必問**（不可逆／對外／花錢／產品決策）：
- `firebase deploy`、`git push`、刪除或遷移資料、放寬 firestore.rules、寄信發通知
- 改變使用者可見的行為或文案方向（這是產品決策，不是實作細節）
- 新增執行期依賴、改資料模型（如 `Booking` 型別加欄位）
- 需求有兩種合理解讀，而選錯的重工成本高

**不問**（自己決定，之後在回報中說明即可）：
- 可逆的局部實作選擇（內部函式命名、測試怎麼組織、helper 放哪）
- 兩條路都可逆且成本低 → 選較保守那條直接做
- 「我可以開始了嗎？」「要繼續嗎？」——**永遠不問這種**

✅ 正例：任務是「修表單驗證」，但正確修法需要動 `Booking` 型別 → 停下來問（超出原範圍＋資料模型）。
❌ 反例：問「錯誤訊息要用什麼措辭？」卻不附選項——要問就給 2–3 個符合 `.impeccable.md` 語氣的候選。
❌ 反例：因為「怕做錯」把可逆的小決定都拿去問——這是把判斷成本轉嫁給使用者。

## R4 方向錯了的訊號（換路，不是重試）

**判準**（符合任一，停止重試）：
- 同一個錯誤在 2 種不同修法後仍然存在（你修的不是病因）
- 每修一處就多壞一處，連鎖 2 次以上
- 你開始想改 `node_modules/` 內、框架原始碼、或生成物（`.next/`）
- 同一段程式碼第 3 次加特例分支
- workaround 上面疊 workaround

**換路程序**：停 → 用一句話重述原始目標（不是重述目前卡住的點）→
列 2 條從目標推出來的替代路線與各自代價 → 選一條或按 R1 升級。

✅ 正例：CSS 蓋不過去，改了兩次 specificity 都沒效 → 停下來查「是不是有兩份樣式來源」
（本專案同時有 Tailwind 與 `src/styles/` 的獨立 CSS）——換診斷路線，不是加第三層 `!important`。
❌ 反例：把「換路」做成「隨機換個檔案繼續改」。替代路線必須能回答「為什麼舊路線失敗」。

## R5 品質底線怎麼驗（按產物類型）

| 產物 | 底線驗證 |
| --- | --- |
| TS/React 程式碼 | `npm run lint && npx tsc --noEmit && npm test`；UI 流程加 `/verify` |
| firestore.rules | `npm run test:rules`（需 Java 21+）；放寬權限的 diff 一律先問使用者 |
| 設定檔（firebase.json、CI…） | 能說出每一行變更的作用；emulator 或 CI 實際起得來 |
| 文件／playbook | 派 `verifier` read-back：「照做會卡在哪」；所有路徑與指令實際存在 |
| 網頁研究結論 | ≥2 個獨立來源、標註來源日期；只有一個來源就標「單一來源」 |
| UI／視覺／文案 | 先讀 `.impeccable.md`；自評「像不像 dashboard template」——像就是錯 |

## R6 誠實條款：這套制度補不了的東西

拆解、驗證、多樣本評審能補**執行品質**；以下兩類補不了，Sonnet 等級尤其要認：

1. **品味題**：UX 好不好、文案語感自不自然、架構的長期取捨。多樣本評審只能剔除爛答案，
   選不出「對這個社群最對味」的答案。
2. **模糊需求**：使用者自己還沒想清楚要什麼的題目。

**遇到時的合法動作（三選一，都要明說）**：
- (a) 界定成使用者決策：給 2–3 個選項附具體取捨，交使用者選
- (b) 派 `second-opinion`（opus）給建議，**並標註信心度**轉述給使用者
- (c) 直說：「這題屬於品味判斷，我的答案不可靠，建議你自己看過再定。」

**禁止**：在品味題上假裝有把握。錯誤的自信比「我不確定」傷害大得多。
本專案的品味錨點是 `.impeccable.md`——它能把一部分品味題轉成可檢查的規則
（低飽和三色、圓角 xl/2xl、反模板感），先用它過濾，剩下的才走 (a)(b)(c)。

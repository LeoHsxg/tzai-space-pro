# 維護協議（maintenance.md）

> 讀者：未來要修改 CLAUDE.md 或 playbooks 的模型。目的：讓制度能更新，但不會被一次糟糕的
> session 改壞。**不確定某個修改屬於哪一級時，按較嚴的那級處理。**

## 1. 權限分級

**🟢 綠級——自行修改，回報中提及即可**
- 在 `lessons.md` 追加教訓（照第 3 節格式）
- 修正已失效的路徑、檔名、指令（前提：先實際驗證新值，引用驗證方式）
- 更新「驗證於 YYYY-MM-DD」的事實並更新日期（同樣要先驗證）
- 修錯字、修壞掉的連結

**🟡 黃級——先向使用者說明「想改什麼＋為什麼」，同意後才動**
- 調整 dispatch.md 的門檻數字、升降級規則、model 對照表
- 刪除或改寫任何一條既有規則、rubric、例子
- 新增檔案到 playbooks/、重組檔案結構
- 修改 `.claude/agents/` 下的 agent 定義
- CLAUDE.md 的任何結構性變動（新增/刪除章節）

**🔴 紅級——不可修改，只能追加註記**
- `letter.md` 的「Fable 5 原始診斷」段落與 `diagnosis.md` 的失效模式分析：
  只能在其下追加「後記（日期）：…」，不能改寫原文。理由：這是制度的基準線，
  改寫它會讓後人無法判斷制度是否已經漂移
- dispatch.md 第 0 節「授權聲明」：範圍變動只能由使用者本人指示

## 2. 修改程序（所有等級通用）

1. 改前備份：複製到 `.claude/backups/<檔名>.<YYYY-MM-DD>.bak`（同檔保留最近 2 份，更舊可刪）
2. 事實先驗證再寫：任何具體事實（路徑、指令、參數名、模型名）都要附驗證方式
   （Grep/Read/實跑過），不能從記憶或舊文件抄
3. 改完 read-back：重讀自己改動的段落，確認沒有把兩條規則改成互相矛盾
4. 大改（黃級以上）：派 `verifier` 對改後全文做一致性檢查
5. 改了 `.impeccable.md` → 同步 `.github/copilot-instructions.md`（兩檔內容相同）

## 3. 教訓寫回：`lessons.md`

踩坑後（被使用者糾正、驗證翻車、規則誤導了你）寫進 `.claude/playbooks/lessons.md`，一行一則：

```
- YYYY-MM-DD｜情境｜錯誤的認知或做法｜正確做法｜證據（commit/檔案/使用者原話）
```

- 寫教訓是 🟢 綠級——**當下就寫，不要等任務結束**（session 隨時可能中斷）
- 同一類教訓出現第 2 次 → 升格提案：把它改寫成對應 playbook 的正式規則（🟡 黃級，先問使用者）
- 教訓要寫「可重用的規則」，不是流水帳。
  ✅「firebase emulators 相關指令在 PowerShell 會因 && 失敗，一律用 Bash tool」
  ❌「今天跑 emulator 失敗了很久才發現原因」

## 4. 膨脹控制（超標時提出精簡提案，🟡 黃級執行）

| 檔案 | 上限 |
| --- | --- |
| CLAUDE.md | 120 行 |
| 各 playbook | 200 行 |
| lessons.md | 150 行（精簡＝合併同類、刪已升格者，不是刪掉沒處理的教訓） |

精簡的原則：CLAUDE.md 每一行是「每個 session 都要付的稅」——內容能移去 playbook 就移，
能用一行路由代替就路由。**永遠不要**在 CLAUDE.md 用 `@路徑` 匯入語法（會被自動載入，破壞路由制的意義）。

## 5. 記憶系統的分工

- **memory 目錄**（`~/.claude/projects/.../memory/`）：使用者偏好、專案目標等「事實」；
  格式照系統提示的 frontmatter 規範
- **playbooks**：程序與規則（怎麼做事）
- **lessons.md**：還沒升格成規則的教訓
- 同一件事不要三處重複記；規則放 playbook，指向它的一行 hook 才放 memory

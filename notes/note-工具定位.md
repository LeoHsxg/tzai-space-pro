話說 client heavy 是一件壞事嗎？

不一定。要看場景：

對這個系統來說，client-heavy 沒問題，因為：

- 頁面內容是「登入後才能看的個人資料」，不需要 SEO
- 資料量小（一個人的借用紀錄不會有幾百筆）
- 即時性比首次載入速度更重要（借用狀態要準確）

**Server Component 的優勢（首次載入快、SEO）**在這裡都用不上。

所以方案 A 完全合理，繼續沿用 client-heavy 就好。

歐首次載入快是關乎用戶留存率，而我這種功能性服務別人本來就需要使用了，因此即時性以及準確率比較重要

---

Firebase Storage 計費三個計費維度：

| 項目     | Spark 免費額度 | Blaze 超額費率   |
| -------- | -------------- | ---------------- |
| 儲存量   | 5 GB $0.026    | / GB / 月        |
| 下載流量 | 1 GB / 天      | $0.12 / GB       |
| 上傳次數 | 20,000 次 / 天 | 極便宜，幾乎不計 |

就算累積超多年，儲存量的計費也還是超級低。下載流量才是重點：每次有人查看照片就會消耗流量。如果照片公開可見、常被查看，這才是真正的費用來源。

瀏覽器開啟任何圖片網址都會下載那個檔案，Firebase Storage 的計費是「資料離開 Storage 就算 egress」，不管是 <img src> 還是用 storage 給的連結都一樣。

| 做法                      | 流量行為                 |
| ------------------------- | ------------------------ |
| 現在的連結（新分頁）      | 點了才下載，一次一張     |
| 展開式 (<img> 直接在 DOM) | 頁面載入就全部下載，很燒 |
| 展開式 + lazy load        | 點了才下載，跟連結一樣   |

如果要用展開式，必須要搭配 lazy load。——只有使用者真的點開的時候才載入圖片。

### GSAP 的優勢

- 時間軸控制（Timeline）：可以精確串接多個動畫，這是 CSS animation 很難做到的
- 緩動函數非常豐富，內建 elastic、bounce 等效果
- 跨瀏覽器一致性比純 CSS 好
- ScrollTrigger 插件：滾動觸發動畫，這是 GSAP 最大的賣點之一

### Framer Motion

- React 原生整合更好
- 有 AnimatePresence 專門處理頁面切換，對你的 Next.js 專案更合適。
- variants — 狀態機式動畫
- whileHover / whileTap / touchstart — 互動微動畫，按鈕、卡片的互動回饋
- layout prop — 佈局變化自動補間，Framer Motion 自動做過渡動畫
